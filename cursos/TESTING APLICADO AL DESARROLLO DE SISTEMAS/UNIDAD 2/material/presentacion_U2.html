UNIDAD 2 — SESION 1

Selección Estratégica
y Herramientas de Prueba

Cómo decidir qué probar, cuándo y con qué herramientas tecnológicas. Adaptación de la estrategia de QA al contexto, la complejidad y los riesgos del proyecto.

Sesion 1

Factores y Contexto en la Selección

El Principio 6 del ISTQB dice: "El Testing depende del contexto". La selección de pruebas es una decisión de inversión financiera, no solo técnica.
Evaluación de Riesgos
Los recursos (tiempo y dinero) son limitados. Seleccionamos el tipo de prueba según:
  • Probabilidad de fallo: ¿Es una tecnología nueva? ¿Equipo junior?
  • Impacto del fallo: ¿Peligro de muerte? ¿Roban datos? ¿Pierde un cliente?
Ejemplo 1: Startup MVP
Objetivo: Salir al mercado en 1 mes.
Selección: Pruebas Unitarias básicas (solo core) y Smoke Tests manuales. No se invierte en Pruebas de Carga pesadas aún.
Ejemplo 2: App Bancaria Core
Objetivo: Procesar transacciones internacionales.
Selección: Pruebas Estructurales estrictas, Test de Seguridad (SAST/DAST) obligatorio, y Pruebas de Estrés.
Sesion 1

El Arsenal del Tester: Herramientas por Nivel

Nivel de Código (Unit/Static)
Las pruebas más rápidas y baratas de ejecutar.

Herramientas clave:
- JUnit / PyTest / Jest (Unitarias)
- SonarQube (Análisis Estático SAST)
Nivel de API (Integración)
Verifican que los microservicios hablen entre sí sin depender del diseño visual UI.

Herramientas clave:
- Postman / Insomnia (Manual/Scripts)
- RestAssured / Newman (Automático)
Nivel de Sistema (UI / E2E)
Prueban el sistema completo como un usuario real. Lentas y frágiles, pero esenciales.

Herramientas clave:
- Selenium / Cypress / Playwright (Web)
- Appium (Mobile)
Nivel No Funcional (Carga/Seguridad)
Prueban estrés, resistencia o vulnerabilidades de inyección.

Herramientas clave:
- JMeter / k6 (Carga y Estrés)
- OWASP ZAP (Pen-testing dinámico DAST)

Desde la ambigüedad del cliente hasta la especificidad técnica. Estructura de User Stories (INVEST) y automatización con Gherkin BDD usando Cucumber.

Sesion 2

Requerimientos vs Historias de Usuario

El Requerimiento Tradicional (SRS)
Típico del modelo Cascada (Waterfall). Documentos extensos, enfocados en el "Qué" debe hacer el sistema desde una perspectiva técnica y a veces incomprensible para el cliente.

"El sistema deberá permitir la autenticación de usuarios contra el LDAP corporativo con encriptación SHA-256 dentro de un tiempo de respuesta < 200ms."
La Historia de Usuario (Agile)
Un recordatorio para tener una conversación. Enfocado en el Valor de Negocio y en el Usuario. Usa lenguaje natural y directo.

"COMO empleado remoto, QUIERO ingresar al sistema usando mi misma clave corporativa, PARA no tener que recordar contraseñas distintas."
Criterio de Calidad: INVEST
Una buena Historia de Usuario debe ser:
Independiente
Negociable
Valiosa
Estimable
Small (Pequeña)
Testeable (Si no es testeable, no sirve)
Sesion 2

BDD, Gherkin y Cucumber en Profundidad

BDD (Behavior-Driven Development): Diseñar pruebas basadas en el comportamiento. Permite que el código de prueba sea leído por Humanos (Clientes) y Máquinas.
Herramienta: Cucumber (Archivo .feature)
En la industria, el archivo Gherkin no es solo un documento Word. Es un archivo que herramientas como Cucumber o SpecFlow leen y "traducen" a funciones de código automático en Java, Python o JS.
# archivo: login.feature Funcionalidad: Retiro de Efectivo Escenario: Retiro exitoso con saldo suficiente DADO que la cuenta tiene un saldo de $1000 Y la tarjeta es válida CUANDO el usuario solicita retirar $200 Y el cajero tiene efectivo disponible ENTONCES el cajero debe entregar $200 Y el saldo de la cuenta debe actualizarse a $800

Diseño de Casos de Prueba
y Trazabilidad en la Industria

Dejando el Excel atrás: La anatomía de un Test Case infalible y cómo asegurar cobertura usando Matrices de Trazabilidad (RTM) modernas como Jira/Xray.

Sesion 3

Anatomía del Caso de Prueba

Un Caso de Prueba (Test Case) documenta variables bajo las cuales un evaluador determinará si la app cumple especificaciones. Debe ser tan claro que alguien nuevo (o un Robot) pueda ejecutarlo sin dudar.
Campo Oficial Descripción Ejemplo Real
ID / Título Identificador único rastreable. TC-001: Validar error por contraseña corta.
Precondiciones Estado exacto del sistema ANTES de empezar. El sistema de BD está arriba. Usuario no logueado. Navegador en URL '/register'.
Datos (Test Data) Archivos o variables exactas a inyectar. user: 'admin', pass: '123' (muy corta).
Pasos a reproducir Acciones explícitas y secuenciales. 1. Ingresar user.
2. Ingresar pass.
3. Hacer click en 'Registrar'.
Resultado Esperado La validación de ÉXITO del caso (No el éxito de la función, sino el de la prueba). El sistema bloquea el submit y muestra alerta roja "Password debe ser > 6 chars".
Sesion 3

Requirement Traceability Matrix (RTM) Moderna

¿Qué es la RTM?
Documento que rastrea cada requerimiento de negocio con sus Casos de Prueba respectivos y su estado actual de ejecución. Garantiza 100% de Cobertura Teórica.
Adiós al Excel: Herramientas
Aunque empezamos en Excel para aprender, la industria usa plugins integrados:
  • Xray o Zephyr (Se integran dentro de Jira).
  • TestRail (Gestión avanzada de test plans y reportes).
En ellos, un caso de prueba se enlaza a un Requerimiento con 1 click.
Req ID Historia de Usuario Test Case ID Asignados Status Cobertura
REQ-01 Como Usuario quiero un Login TC-001 (Positivo), TC-002 (Error) Cubierto (Pass)
REQ-02 Recuperar Clave TC-003 Cubierto (Run pending)
REQ-03 Bloqueo tras 3 intentos (Seguridad) ¡NO HAY TEST CASOS! HUECO DE COBERTURA

El Master Test Plan
(Estándar IEEE 829)

El documento rector que unifica requerimientos, tipos de prueba, herramientas y cronogramas. Cómo planificar recursos y defender tu estrategia ante inversores.

Sesion 4

Estructura del Test Plan Maestro (IEEE 829)

El Plan de Pruebas es el documento estratégico y directivo. No detalla CÓMO apretar un botón (eso es un Test Case), sino el QUÉ, QUIÉN, CUÁNDO y CON QUÉ.
1. Alcance (In / Out)
Define explícitamente qué se va a probar (ej. Funcionalidades críticas) y, vitalmente, qué NO se va a probar (ej. Integraciones de terceros). Protege al QA de expectativas imposibles.
2. Entorno y Recursos
Hardware y Software necesario. (Ej: "Necesitaremos 3 servidores AWS EC2 con base de datos de staging clonada").
¿Quién hace qué? (Asignación de QA Analysts).
3. Criterios Entry/Exit
Entry: Requisitos para empezar a probar (Ej: Código pasó CI/CD).
Exit: Condiciones para terminar (Ej: "100% bugs críticos resueltos, matriz RTM ejecutada").
Actividades Sincrónicas — Sesion 4

Presentación ejecutiva (20 min por grupo).

Deben defender sus Criterios de Exclusión (Out of Scope) y explicar por qué sus tipos de prueba y herramientas seleccionadas ahorran dinero o previenen desastres financieros.

El Encargo (3 Entregables)

Partes de la Evaluación 2

1. La Matriz RTM
Identifica 3 algoritmos clave del repositorio (Tómalos como tus Requerimientos Funcionales). Crea una Hoja de Cálculo (Excel) construyendo una RTM que enlace estos 3 Requerimientos con al menos 5 Casos de Prueba Formales en total (recicla los de la U1 y agrega nuevos). ¡Asegura 100% de cobertura!
2. Escenarios BDD Gherkin
Para los algoritmos identificados, redacta 4 escenarios formales usando sintaxis Gherkin (DADO, CUANDO, ENTONCES) en un documento PDF.

Obligatorio: Debes incluir escenarios de éxito y escenarios donde el algoritmo reciba "basura" (ej. null o letras en vez de números) simulando un UAT estricto.
3. Master Test Plan
Crea el Test Plan en PDF (Basado en IEEE 829). Debe contener:
  • Alcance (In/Out): ¿Qué probarás y qué NO del repo?
  • Entorno: Herramientas exactas a usar (Revisa Sesión 1).
  • Criterios: Entry / Exit Criteria.
Entrega Final: Sube tu Excel (RTM + Casos) y PDF (Gherkin + Test Plan) a la plataforma EVA. Formatos .zip o .rar serán calificados con la nota mínima.
