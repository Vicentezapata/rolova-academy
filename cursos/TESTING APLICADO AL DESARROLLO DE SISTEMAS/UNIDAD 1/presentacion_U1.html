Sesion 1

El Costo del Error a través del Ciclo (SDLC)

El "Efecto Bola de Nieve": Un error arquitectónico detectado en Producción obliga a reescribir código, migrar datos y parchar APIs.
Ariane 5 (Pérdida Financiera)
Se reutilizó código del Ariane 4 que asumía velocidades menores. Al superar la velocidad límite, una variable float de 64-bit causó un overflow al convertirse en un int de 16-bit.

Consecuencia: Pérdida total en 37s ($370M). Lección: Reutilizar código sin probar el nuevo contexto viola principios de testing.
Knight Capital (Pérdida de Negocio)
En 2012, un código huérfano (no testeado durante un despliegue) se activó por error, ejecutando millones de compras de acciones en minutos.

Consecuencia: Pérdida de $440M en 45 min y quiebra. Lección: Faltaron pruebas de regresión y aislamientos de entorno.

Sesion 1

Los 7 Principios (Parte 1: 1 al 4)

01
El testing muestra defectos
El testing puede demostrar empíricamente que existen defectos, pero no puede probar matemáticamente que no los hay. El testing reduce la probabilidad de fallas ocultas, pero no es una garantía absoluta de perfección.
02
El testing exhaustivo es imposible
Probar TODAS las combinaciones de datos (entradas, precondiciones, estados) es inviable. Una simple pantalla de login con 2 campos de 10 caracteres genera trillones de combinaciones. Se debe priorizar por riesgo corporativo.
03
Testing temprano (Shift-Left)
El testing no es una "fase al final". Debe comenzar en el levantamiento de requisitos. Validar un diseño o un documento de arquitectura ahorra tener que re-codificar sistemas enteros meses después.
04
Agrupación de defectos (Pareto)
El 80% de los defectos operativos suele concentrarse en el 20% de los módulos centrales. Los sistemas de pago o integración legacy suelen ser nidos de bugs. Allí debe ir el esfuerzo de QA.
Sesion 1

Los 7 Principios (Parte 2: 5 al 7)

05
La paradoja del pesticida
Si corres los mismos 100 tests todos los días, dejarán de encontrar bugs nuevos, porque el código ya se inmunizó contra ellos (ya se arreglaron). Los tests deben ser revisados, rotados y ampliados constantemente para explorar nuevos caminos del software.
06
El testing depende del contexto
No se puede usar la misma metodología para todo. Una web promocional de Coca-Cola requiere énfasis en UI/UX y cargas masivas rápidas, pero puede tolerar un bug menor. Un software de control de tráfico aéreo requiere rigor matemático, certificación DO-178C y tolerancia cero a fallas.
07
La ilusión de la ausencia de defectos (Falsa Seguridad)
Puedes tener un sistema con cobertura de código 100%, automatizado perfectamente, y 0 bugs reportados... pero si el software es difícil de usar, no cumple las normativas legales actuales, o no es lo que el cliente realmente necesitaba para su proceso de ventas, el proyecto es un fracaso absoluto. Calidad no es solo "falta de errores".

Sesion 2

Testing Unitario Aislado: Mocks y Stubs

Una Prueba Unitaria genuina NUNCA debe conectarse a una base de datos real, red, ni sistema de archivos. Debe ser 100% aislada (pura en memoria).
¿Qué pasa si mi función necesita leer de BD?
Se utilizan Dobles de Prueba (Test Doubles): objetos falsos programados para simular el comportamiento de las dependencias externas.
  • Stubs: Devuelven datos "harcodeados" fijos. (Ej: "Cuando llamen al servicio Clima, devuelve siempre 25°C").
  • Mocks: Verifican interacciones. (Ej: "Verificar que el servicio de Email fue llamado exactamente 1 vez con el parámetro X").
# Función original a probar def liquidar_sueldo(empleado_id, BD, BancoAPI): empleado = BD.obtener(empleado_id) sueldo = empleado.sueldo_base - impuesto BancoAPI.transferir(empleado.cuenta, sueldo) return True # Test Unitario (pytest) usando Mocks def test_liquidar_sueldo(mocker): # Arrange: Preparamos los dobles mock_BD = mocker.Mock() mock_BD.obtener.return_value = Empleado(sueldo_base=1000) mock_Banco = mocker.Mock() # Act: Ejecutamos función resultado = liquidar_sueldo(1, mock_BD, mock_Banco) # Assert: Verificamos assert resultado == True mock_Banco.transferir.assert_called_once_with(cuenta, 800)
Sesion 2

Pruebas de Integración: Topologías de Ensamble

Enfoque Big Bang (Evitar)
Se espera a que todos los módulos estén codificados y se unen de una sola vez.

Problema crítico: Si el sistema falla, es increíblemente complejo aislar cuál de las 50 conexiones nuevas fue la que provocó el fallo. Produce cuellos de botella masivos al final del ciclo.
Top-Down (De UI a BD)
Se prueba el flujo principal de control primero (el orquestador). Los módulos de bajo nivel que aún no existen se reemplazan por Stubs.

Ventaja: Valida tempranamente la arquitectura global y la lógica de negocio mayor.
Bottom-Up (De BD a UI)
Se prueban primero los componentes base (ej: acceso a datos). Para probarlos sin la UI superior, se construyen Drivers (programas temporales que los llaman).

Ventaja: Los cimientos técnicos quedan hiper-validados desde el día 1.
Integración Continua (CI)
La topología estándar de la industria ágil (DevOps). Cada commit de código ensambla y testea la integración automáticamente en un servidor (Jenkins, GitHub Actions). Detecta roturas instantáneamente.

Sesion 3

Pruebas de Sistema (System Testing)

El entorno de prueba debe ser idéntico o homólogo al entorno de producción (hardware, red, configuración). Se evalúa la "caja negra" completa.
Vertiente 1: Verificación Funcional Completa
Se valida que el sistema cumple explícitamente con los Requisitos Funcionales del documento de especificación (SRS).
  • Pruebas End-to-End (E2E) de flujos de usuario largos (Ej: Registro -> Compra -> Despacho).
  • Verificación de interfaces gráficas completas (UI).
  • Validación de persistencia real en la Base de Datos.
Vertiente 2: Atributos de Calidad (No Funcional)
El sistema hace lo correcto, pero ¿lo hace BIEN y de forma segura?
  • Carga (Load): ¿Soporta 1,000 usuarios concurrentes sin degradarse?
  • Estrés (Stress): ¿Qué pasa si inyectamos 10,000 usuarios? (Validar que el fallo sea controlado).
  • Seguridad: Inyección SQL, Cross-Site Scripting, accesos de roles no autorizados.
Sesion 3

Pruebas de Aceptación (UAT): Fases

La meta final: El "Sign-off"
El UAT no es para encontrar bugs (si hay bugs obvios aquí, la fase de Sistema falló). Su único objetivo es obtener la firma de aceptación formal del cliente para liberar el pago y pasar a producción.
Pruebas Alpha
  • Se realizan en el entorno de los desarrolladores (in-house).
  • Ejecutadas por un grupo interno selecto o stakeholders internos.
  • El entorno está totalmente controlado por la empresa de software.
  • Último filtro fuerte antes de exponer el producto al mundo.
Pruebas Beta (o Pilotaje)
  • Se realizan en el entorno de los clientes/usuarios reales.
  • El desarrollador pierde control del hardware y red donde se ejecuta.
  • Feedback real ("Beta pública" de juegos o software SaaS).
  • Mide adopción, usabilidad subjetiva e imprevistos ambientales.
Sesion 3

Generación de Criterios de Aceptación (BDD)

Para evitar los requerimientos vagos del cliente ("Quiero que el sistema sea rápido y seguro"), usamos Behavior-Driven Development (BDD) y lenguaje Gherkin.

  • Gherkin es un lenguaje puente entre el Negocio y QA/Desarrollo.
  • Fuerza a ser específicos y medibles.
  • Permite automatizar fácilmente usando herramientas como Cucumber o Behave.
Sintaxis Fundamental:
DADO (Given): El estado inicial o precondición.
CUANDO (When): El evento o acción que dispara la prueba.
ENTONCES (Then): El resultado observable o medible.
Ejemplo de Traducción a Gherkin
Requisito Vago
"El login debe bloquear la cuenta si intentan hackear."
Criterio de Aceptación (Gherkin) 
Escenario: Bloqueo por fuerza bruta
DADO que existe un usuario "juan@mail.com" activo
Y la política de bloqueo es de 3 intentos

CUANDO ingresa contraseñas erradas 3 veces seguidas
Y presiona el botón de Ingreso

ENTONCES el sistema debe cambiar su estado a "Bloqueado"
Y enviar un email de alerta de seguridad
Y no permitir el login en los próximos 15 minutos.
Sesion 3

Estructura de Escenarios Gherkin y Buenas Prácticas

CUANDO... ENTONCES (Acción Única)

Úsalo para acciones atómicas y aisladas del usuario. Mantiene tus escenarios pequeños, legibles y altamente específicos para una sola regla de negocio.

Ejemplo: Acción Atómica 
DADO que el usuario está en la página de pago
CUANDO el usuario hace clic en "Realizar Pedido"
ENTONCES debe mostrarse la confirmación del pedido
CUANDO... Y... ENTONCES (Acciones Encadenadas)

Úsalo cuando una historia requiere una secuencia de acciones interdependientes para alcanzar el estado final. Los pasos intermedios "Y" representan estados transicionales.

Ejemplo: Flujo Secuencial 
DADO que el usuario tiene un artículo en su carrito
CUANDO el usuario ingresa su código de descuento
Y el usuario selecciona envío rápido
Y el usuario hace clic en "Realizar Pedido"
ENTONCES debe mostrarse la confirmación del pedido
Buenas Prácticas en Gherkin
Evitar "Y entonces" (And then)

En la sintaxis Gherkin estándar, no existe una palabra clave técnica "Y entonces". En su lugar, simplemente utilizas Y (And) como una continuación limpia de un CUANDO o de un ENTONCES.

Cuidado con la Sobrecomplicación

Si te encuentras encadenando demasiados pasos CUANDO e Y (más de 3 o 4 pasos transicionales), es muy probable que el escenario esté intentando cubrir demasiados casos de uso a la vez. Es mejor dividirlo en escenarios distintos e independientes.

Regla de Oro en BDD:

Cada escenario debe validar una única regla de negocio medible. La claridad para el negocio siempre está por sobre ahorrar líneas de código.

Plan de Prueba vs. Casos de Prueba

Para entender cómo probar un sistema, debemos diferenciar la estrategia global de la ejecución específica, y cómo estos se mapean a los Niveles de Prueba.

Test Plan (Plan de Prueba)
Es el documento maestro o estratégico. Describe el alcance, enfoque, recursos y cronograma de las actividades de prueba.
  • Propósito: Responder al "¿Qué vamos a probar y cómo nos organizamos?"
  • Relación con Niveles: Un Plan abarca todos los niveles (define cuándo se hacen las Unitarias, cuándo el UAT, etc).
  • Ejemplo: "Plan de Prueba para el Módulo de Pagos Q3".
Test Case (Caso de Prueba)
Es el escenario táctico y reproducible. Conjunto de precondiciones, inputs, acciones y resultados esperados.
  • Propósito: Responder al "¿Cuáles son los pasos exactos para verificar esta función?"
  • Relación con Niveles: Cada Caso de Prueba pertenece a un nivel específico (Ej: Caso Unitario, Caso de Sistema).
  • Ejemplo: "Login con password vacío".

Sesion 4

Caja Blanca vs. Caja Negra: Técnicas

Caja Blanca
if(x>0) {...}
VS
Caja Negra
IN → ??? → OUT
CAJA BLANCA (Estructural)
¿Qué medir matemáticamente? (Cobertura)
  • Sentencias: ¿Se ejecutó cada línea de código al menos una vez?
  • Decisiones (Branches): ¿El IF y el ELSE fueron recorridos en tests separados?
  • Mutaciones: Si altero el código a propósito, ¿mis tests fallan?
CAJA NEGRA (Funcional)
¿Cómo diseñar tests sin ver el código?
  • Valores Límite (BVA): Probar justos los bordes. Si acepta 1 a 100, probar 0, 1, 100 y 101.
  • Partición de Equivalencia: Elegir valores aleatorios dentro de clases válidas e inválidas para reducir repetición.
  • Transición de Estados: Evaluar los flujos de "Enviado -> Pagado -> Despachado".
Sesion 4

Cómo Diseñar un Caso de Prueba Formal

Un Caso de Prueba (Test Case) documenta un escenario específico para verificar una funcionalidad concreta. Su objetivo es que sea reproducible por cualquier otro QA.

  • Precondiciones: El estado exacto del sistema ANTES de la prueba (ej: "Usuario logueado").
  • Datos de Prueba: Qué inputs vamos a inyectar (ej: "RUT = 12345678-9").
  • Pasos a Ejecutar: Secuencia cronológica y determinista (1. Click aquí, 2. Escribir allá).
  • Resultado Esperado: Qué debe pasar matemáticamente o visualmente (el test FALLA si el resultado real es distinto al esperado).
Plantilla Estándar en la Industria
ID: CP-LOGIN-01
Nombre: Login con credenciales inválidas
Nivel: Sistema | Técnica: Caja Negra (Equivalencia)

Precondición: Estar en la URL /login. DB limpia.
Datos: usuario="test@test.com", pass="errado"

Pasos:
 1. Escribir usuario en input 'email'
 2. Escribir pass en input 'password'
 3. Click en botón 'Ingresar'

Resultado Esperado:
 - No debe iniciar sesión.
 - Debe aparecer toast rojo: "Credenciales inválidas"
 - Tiempo de respuesta < 1s.
Sesion 4

Regresión Exhaustiva vs. Sanity Checks

El Testing de Regresión asegura que el nuevo código introducido (un bug fix o nueva feature) no haya roto, colateralmente, el software funcional existente.
Selección de Suite de Regresión
En grandes corporaciones, una suite completa de regresión puede tardar de 10 a 24 horas en correr. No se puede ejecutar completa en cada commit.

Estrategia de priorización: Ejecutar pruebas enfocadas al módulo que fue alterado, o depender de la automatización en la Nube (AWS/Azure) con CI/CD de integración diaria.
Sanity Testing (Prueba de Cordura)
Es un subconjunto mínimo y muy acotado de la prueba de regresión.

Propósito: Cuando el equipo de dev hace un despliegue crítico de emergencia (Hotfix), QA hace un "Sanity" rápido de 15 minutos solo al componente tocado, para confirmar que la aplicación "sigue cuerda" y el fix funcionó, antes de proceder con pruebas completas.

Smoke Testing (Prueba de Humo): Similar, pero enfocado solo a las funcionalidades absolutamente vitales (Ej: Login y Pagar). Si falla, se devuelve a dev inmediatamente, "echando humo".

Funcionales: Base y End-to-End

Unitarias (Función/Método)
¿Qué es? Prueba la pieza de código más pequeña de forma aislada.
Herramientas: JUnit (Java), PyTest (Python), Jest (JS).
Objetivo: Asegurar que la lógica matemática o condicional interna sea perfecta.
Integración (Módulos)
¿Qué es? Prueba cuando 2 o más unidades se comunican entre sí.
Herramientas: Postman, RestAssured.
Objetivo: Validar el contrato de datos (ej: el Backend recibe lo que el Frontend envió).
Sistema (End-to-End)
¿Qué es? Prueba el sistema completo ensamblado, tal cual lo usará el cliente.
Herramientas: Cypress, Selenium, Playwright.
Objetivo: Detectar fallas de infraestructura o flujos de usuario rotos.
Aceptación (UAT / Alfa / Beta)
¿Qué es? Prueba final ejecutada por los clientes o Product Owners.
Herramientas: Cucumber (BDD), Excel/TestRail.
Objetivo: Validar si el software realmente resuelve el problema de negocio.

Humo (Smoke) y Sanidad
Humo: Prueba hiper-rápida (5 min) para ver si la app "enciende" tras un despliegue.
Sanidad: Prueba enfocada solo en el bug que el developer jura haber arreglado recién.
Objetivo: Evitar perder tiempo testeando a fondo una versión que viene rota de fábrica.
Regresión y Confirmación
Regresión: Asegurar que un código nuevo no haya roto cosas viejas que sí funcionaban. Fundamental automatizarlas.
Confirmación: Retestear un bug reportado para confirmar que se solucionó y cerrarlo en Jira.
API y UI (Niveles Visuales e Internos)
Pruebas de API: Pruebas backend directas a los endpoints (sin diseño gráfico). Son ultra rápidas, estables y seguras.
Herramientas: Insomnia, SoapUI.
Pruebas de UI: Interacción visual simulando clicks en botones y completando formularios web/móvil.
Herramientas: Appium (Móvil), Selenium.
Pruebas No Funcionales

No Funcionales: Rendimiento y Seguridad

Rendimiento (Performance)
  • Carga: 100 usuarios normales, ¿cuánto demora en cargar?
  • Estrés: 10.000 usuarios, ¿dónde colapsa el servidor?
  • Picos (Spike): Black Friday. De 0 a 1M usuarios en un segundo.
  • Resistencia (Soak): 50 usuarios constantes por 48 horas (buscando fugas de memoria).
Herramientas: JMeter, k6, Gatling, LoadRunner.
Seguridad
  • Pentesting: Hackers éticos manuales buscando vulnerabilidades explotables.
  • SAST (Estático): Bots que leen tu código fuente buscando malas prácticas (ej: contraseñas hardcodeadas).
  • DAST (Dinámico): Bots que atacan tu web en ejecución (ej: inyectando SQL en los inputs).
Herramientas: SonarQube (SAST), OWASP ZAP (DAST), Burp Suite.
Pruebas No Funcionales

No Funcionales: Experiencia y Entorno

Usabilidad (UX)
¿Qué es? Mide la facilidad con la que una persona real usa el sistema.
  • Heurística: Expertos evalúan si cumple leyes de diseño (ej: Nielsen).
  • Usuarios: Pruebas de "Heatmaps" y grabaciones de sesión.

Herramientas: Hotjar, CrazyEgg, Figma Prototypes.
Compatibilidad
¿Qué es? ¿Se ve bien en Chrome, Safari y Firefox? ¿Funciona en Android 10 y iOS 17? ¿En pantalla gigante y celular pequeño?

Mantener laboratorios físicos de celulares es muy caro, por lo que se usa la nube.

Herramientas: BrowserStack, Sauce Labs.
Instalación y Localización (L10n)
Instalación: Asegurar que la App se instale, actualice y desinstale sin dejar basura en el sistema operativo del usuario.
Localización: Adaptar idioma, zona horaria, formatos de moneda y diseño (ej: el árabe se lee de derecha a izquierda).
Pruebas Funcionales

Funcionales: Tendencias de Industria

Exploratoria
¿Qué es? Testing libre sin casos de prueba estrictos. Depende de la intuición y experiencia del QA para "romper" la app.

Herramientas: Xray Exploratory App, Session-Based Testing.
Contrato (Contract)
¿Qué es? Valida que dos microservicios se comuniquen respetando un esquema acordado (contrato) sin levantar todo el entorno E2E.

Herramientas: Pact, Spring Cloud Contract.
Mutación
¿Qué es? "Probar las pruebas". Inyecta bugs a propósito en el código base para verificar si los tests unitarios son capaces de detectarlos y fallar.

Herramientas: Stryker (JS/C#), PIT (Java).
Pruebas No Funcionales

No Funcionales: Nuevas Tendencias

Chaos Engineering
¿Qué es? Apagar servidores aleatoriamente en producción para probar la resiliencia y el "Disaster Recovery". Netflix lo popularizó.
Herramientas: Chaos Monkey, LitmusChaos.
Accesibilidad (a11y) y Compliance
a11y: Asegurar que personas con discapacidades (visuales, motoras) puedan usar la app mediante lectores de pantalla (Leyes WCAG/ADA).
Compliance: Pruebas legales para GDPR (Europa) o leyes de protección de datos.
Otras menciones vitales en Enterprise
A/B Testing: Mostrar 2 versiones distintas de la UI a usuarios diferentes para medir estadísticamente cuál genera más ventas/clicks.
Migración de Datos (ETL): Pruebas críticas al cambiar de base de datos o sistema. Valida que no se pierda ni mutile la data del cliente.
